**Status: design.** Nothing here is built. It settles *how* work should carry across
sessions and across harnesses, because the obvious answer — capture more at session end —
was already tried here and removed on purpose.

A session ends. Its decisions are in the corpus if someone ran `/debrief`, and lost
otherwise. The next session, possibly in a different harness, starts from a briefing that
cannot tell it what the previous one did or which of its own commitments the work closed.
That gap is the subject.

## What was already tried

<Note>
**Product decision, 2026-06-11 — capture transport removed.** The mechanical
`PostToolUse` capture hook was killed end-to-end (migration 0010, promoted to main and
applied to prod). Rationale: a `PostToolUse` hook only sees tool I/O, so it can log
mechanical *what happened* — already in git and GitHub, carrying no *why*, and adding
retrieval noise. The recorded lesson: **value comes from intentional writes, LLM-summarized
decisions, and orientation — not from auto-scraping tool events.**
</Note>

The damage was structural rather than per-item, which is the part worth remembering
because it is counterintuitive:

| Symptom | Measurement |
|---|---|
| Volume dominance | 897/1177 (76%) of hook memories were legacy `commit:`/`session-end` rows |
| Payload bloat | one commit capture swallowed a ~10 KB audit report via pattern matching |
| Null-value writes | session-end emitted `Files modified: …, Commits: none` when everything was zero |
| Cluster distortion | including hooks moved clustering 75 → 99, one cluster holding 47× `commit: engram` |
| Suppression debt | 0.5× search dampening, `cluster_exclude_sources=['hook']`, plus a digest job to archive |
| Parallel attempt | GitHub commit sync produced 619 rows with no embeddings, no scope, no tags |

Yet a 200-memory sample scored **98% signal** (63% HIGH, 35% MEDIUM, 2% NOISE). Per-item
quality was fine and the filters worked. Mechanical captures share a syntactic shape, so
they collapse into source-shape clusters and dominate by count — a corpus can be wrecked
by rows that are individually useful. **Judge a capture mechanism by what it does to the
corpus, not by spot-checking its rows.**

## But the curated path has a measured hole

The same decision blessed `/debrief`. A coverage audit over 10 sessions then measured that
path:

| Metric | Result |
|---|---|
| Overall recall | **26%** (50 candidates, 13 matched, 37 missed) |
| Commitment recall | **0%** |
| Decision / project / user recall | 25% / 29% / 33% |
| Spurious captures | none |

with a structural cause: `PostToolUse` fires on tool events only, so user-turn feedback and
preferences *cannot* be hook-captured at all, and `/debrief` only runs when a human
remembers to type it.

So both positions have holes. Mechanical capture pollutes; curated capture misses
three-quarters of what matters. **The gap was never a missing capture mechanism — it is
that the good mechanism fires unreliably.**

## What the misreporting evidence actually shows

The intuitive fix is to capture verification evidence (git SHA, files touched, test exit
codes) so a handoff reflects what happened rather than what an agent claims. The corpus
contains four documented misreportings, and they do not support it:

| Incident | What happened | Would exit-code capture catch it? |
|---|---|---|
| Dep-audit gates (2× in one batch) | Both sub-agents reported `npx <tool> exits 0` locally; both failed CI. Cause: hoisted `node_modules` vs CI's `npm ci --workspaces=false` | **No — it captures `0` and certifies the wrong answer** |
| Fabricated symbols | An agent invented five nonexistent function names; review caught all five | No — needs source reads |
| Stale-diff review | 4 review agents on a 254-file diff; all 4 blocking findings false | No |
| Stale memories | **6 instances in one session**: a PR called "the only open PR" had merged 5 days earlier; an item said "reserve the npm name" when it was published; one item sat blocked ~4 months on a gate that had already cleared | No — the failure is read-side |

The one case of "a gate reported green when it wasn't" is precisely the case where
mechanical capture would have recorded green, now with the authority of evidence. The
frequent, recent, still-recurring failure is the fourth row, and its recorded cause is
that **nothing re-checks an externally-gated item when its gate clears**.

## Hook mechanics

The design is constrained by what the harness actually permits.

| | `Stop` | `SessionEnd` |
|---|---|---|
| Fires | after each turn | session already terminating |
| Receives | `last_assistant_message`, `stop_hook_active`, `session_id`, `cwd` | `session_id`, `transcript_path`, `cwd`, `reason` |
| Inject context | **yes** | no — there is no model call left |
| Make the agent work | **yes** — `decision: "block"` continues the turn | no |
| Budget | normal timeout | 1.5 s shared (Claude) / 1 s default, 3 s max (Codex) |

Two consequences:

1. **A debrief cannot run at `SessionEnd`.** By then there is nobody to instruct. This is
   why `3ngram-hook sync` sits at that event and is a deliberate no-op
   (`cmd/3ngram-hook/sync.go:38`) — pushing files needs no model, and that slot cannot be
   upgraded into a triage. Codex states this structurally: `SessionEnd` is the **only**
   event with no output schema generated for it at all, and the docs say its output
   "won't steer Codex or keep the thread open."
2. **`Stop` is the only hook that can make an agent reconcile its own work.** It fires
   **once per turn**, not once per session, which makes gating the central design problem
   rather than a detail.

### Both harnesses support this, with different wire shapes

Verified against Claude Code's hook reference and `openai/codex` at `rust-v0.147.0`
(generated schemas under `codex-rs/hooks/schema/generated/`, plus
`hooks/src/events/stop.rs` and `core/src/session/turn.rs`).

| | Claude Code | Codex CLI |
|---|---|---|
| Blocking `Stop` | yes | **yes** |
| Gets final message | `last_assistant_message` | `last_assistant_message` |
| Where injected text goes | `hookSpecificOutput.additionalContext` | **`reason`** — no `hookSpecificOutput` on `Stop` |
| Continue semantics | block → agent keeps working | block → `reason` becomes a **new user prompt** |
| Loop guard | `stop_hook_active` | `stop_hook_active` only — **no built-in cap** |
| Alternate path | exit 2, stderr to agent | exit 2, stderr carries the text |

Codex hooks are **stable and enabled by default** (`Stage::Stable`, `default_enabled: true`
in `codex-rs/features/src/lib.rs`); the `codex_hooks` feature flag is a deprecated alias
and is no longer required. This supersedes the 2026-05-07 reading that treated hooks as
flag-gated.

<Note>
**The payload is not portable — the trigger logic is.** Codex's `Stop` output schema has no
`hookSpecificOutput` and no `additionalContext`; the continuation text rides in `reason`,
and `decision: "block"` with a blank `reason` is a hook *failure* that produces no
continuation. So `3ngram-hook` must emit a different envelope per harness while the
decision of *whether* to fire, and the text itself, stay shared. That is precisely the
split this design already assumes: 3ngram owns the words, the hook owns the trigger.
</Note>

**Codex has no continuation cap.** The turn loop sets `stop_hook_active` and continues with
no counter bounding how many times a `Stop` hook may re-block. The hook must self-terminate.
That promotes the gate below from an ergonomic concern to a **safety requirement** — an
ungated triage is an infinite turn loop on Codex, not merely an annoying one. Note also that
matching hooks launch concurrently with no ordering guarantee, and multiple blocking `Stop`
reasons are joined with `\n\n`.

## Recommendation

Three layers, in dependency order. None writes to the corpus and none consumes a tool slot.

### 1. Session provenance on `memory_events` (no migration)

`memories` carries no provenance — no `source`, no `session_id`, no metadata column. But
`memory_events` already has the shape:

```sql
CREATE TABLE "memory_events" (
  "memory_id"  uuid NOT NULL,
  "event_kind" text NOT NULL,  -- create|revise|supersede|resolve|unresolve|archive|import|embed_failed
  "actor_kind" text NOT NULL,  -- user_dashboard|user_api|user_mcp|worker|importer|system
  "payload"    jsonb,          -- nullable, and unconstrained on the native write path
  "created_at" timestamptz NOT NULL
);
```

Write `{ session_id, agent, project }` into `payload` on the `create` event — and on
`revise` and `resolve` too.

The hook authenticates with the user's API key, so it writes as `actor_kind: 'user_api'`.
No new actor kind, and therefore no constraint migration — which matters, because
`0010_drop_capture_hook_actor_kind.sql` deliberately *removed* `capture_hook` from this
constraint as the final step of the 2026-06-11 removal. Reintroducing a hook-shaped actor
would reverse that; `user_api` is both accurate and uncontentious.

<Note>
**This is the architectural line between this design and the system that was removed.**
The old hook wrote rows in `memories`: new retrievable objects competing in search,
clustering into source-shape bubbles, needing dampening to suppress. Provenance writes
rows in `memory_events`, which is **not in the retrieval path**: no reference in
`packages/db/src/search.ts`, `briefing-read.ts`, `packages/core/src`, or the consolidation
worker. Corpus size, embedding count and cluster geometry are all unchanged. The
2026-06-11 decision rejected auto-scraping *into the corpus*; it says nothing against
metadata on writes the agent already chose to make.

The one read outside the dashboard and GDPR export is an embedding-repair selector
(`memory-embedding.ts:122-127`) filtered on `event_kind = 'embed_failed'`, which a
provenance event cannot match.
</Note>

Annotating revisions is safe, though for a narrower reason than "nothing is touched."
`reviseMemory` **does** update the predecessor row — it stamps `valid_to` and `updated_at`
(`packages/db/src/memory-revise.ts:227-237`). What it never touches is **content, topic or
tags**; the append-and-supersede guarantee is a content guarantee, not row immutability.
Provenance lands in `memory_events` regardless, never on the memory. Revisions are in fact
the *interesting* case: "which session corrected this, and was it Claude or Codex" is the
cross-harness question.

**Keep the payload minimal — `session_id`, `agent`, `project`.** Not `transcript_path` or
`cwd`: both embed the local home directory and machine layout, and memories are shareable.

### 2. A gated `Stop` triage

3ngram already serves the words. `apps/server/src/mcp/prompts.ts:170` registers a
`debrief` prompt instructing the agent to extract decisions, commitments, follow-ups and
preferences, persist each via `remember`, and *"for any commitment COMPLETED this session,
call the `resolve` TOOL on its memory id."*

MCP prompts are user-invoked; a server cannot push one. So the hook must fetch that text
and inject it with `decision: "block"`. **3ngram owns the words, the hook owns the
trigger** — which is what buys cross-harness parity, since both harnesses then read
identical instructions from one source.

<Warning>
**The prompt text is not reachable over REST today.** `debrief` is served only through MCP
`prompts/get` on `/mcp`; no REST route exposes prompt text, and the hook binary has no MCP
client. Either a REST route for prompt text is added, or the text is duplicated into the
hook — and duplicating it forfeits the single-source property that makes cross-harness
parity work. This is new surface, not existing surface.
</Warning>

Two things the shipped prompt does not do, and they are the useful additions:

- It never **re-reads the memories this session wrote**. Provenance makes that a query.
- It extracts from the conversation only, never **querying pre-existing open commitments**
  the work may have closed. That is the 0%-commitment-recall hole and the stale-gate
  failure, which are the same failure seen from two directions.

With provenance the gate is a query rather than a heuristic:

| Condition | Source |
|---|---|
| `stop_hook_active` is false | hook stdin |
| memories created this session > 0, **or** briefed commitments exist | `memory_events` |
| no triage event already recorded for this session | `memory_events` |

Fires once per session, on real signal, provably not twice. Without provenance this
degrades into guessing from turn counts and file mtimes — and on Codex, which has no
continuation cap, a mis-gated triage is an infinite turn loop.

<Warning>
**The gate depends on a read that the codebase deliberately prevents.** The only reader of
`memory_events` redacts payload by construction: `memory-history-queries.ts:196-199`
selects `payload IS NOT NULL`, `jsonb_typeof` and `octet_length` but never values, and
`packages/schema/src/rest.ts:311-322` documents that as intentional — *"never raw payload
values or arbitrary payload keys."* Reading `session_id` back out is exactly the shape that
rule forbids.

That rule exists because payload is untyped and could carry anything. The resolution is a
**typed provenance read** that projects only a known-safe key set (`session_id`, `agent`,
`project`) rather than relaxing the general rule — but it is a real design decision, not
plumbing, and it should be settled before step 2 is built.
</Warning>

### 3. A `SessionEnd` seal

Side effects are unrestricted at `SessionEnd`; only model interaction is barred. The
budget is tight in both harnesses — 1.5 s shared on Claude, 1 s default and 3 s hard max on
Codex — so this must be a single fire-and-forget POST. Its job is **not** capture:
`remember` already wrote the memories. It marks the session closed with a cursor, which is
what makes *"what changed since you last looked"* computable at the next `SessionStart`, in
any harness. Read-side enablement, not capture.

Prior art: engram issue **#4774** specified *"a provenance-rich, cursor-based change feed
(replayable since cursor X)"* for external ingest. That is substantially this layer, reasoned
through once already. It was never built here and has no equivalent issue in this repo, but
the cursor semantics should be taken from it rather than re-derived.

## Cost to the tool budget: zero tools, but not zero surface

Eleven tools are registered (`MAX_TOOLS = 12`) with one slot left and no reservation on it,
and [threads](/concepts/threads) is the leading claimant. Per
[MCP surface budget](/concepts/mcp-surface), prompts and resources cost no slot. **This
design must not need a tool, and it does not.**

It does need new surface, and the earlier claim that it rides entirely on existing routes
was wrong. Nothing here requires a migration; all of it requires code:

| Needed | Why it does not exist today |
|---|---|
| Provenance on the write contracts | `rememberInputSchema` is `.strict()`, so nothing can ride along as an extra field |
| `payload` plumbed through `writeMemory` | It hardcodes `payload: undefined` (`memory-write.ts:220`) |
| A `payload` parameter on commitment transitions | `transitionCommitment` has none (`commitments.ts:276-284`) |
| A typed provenance read | The sole reader strips payload values by design |
| A REST route serving prompt text | Prompts are MCP-only; the hook has no MCP client |

## Relation to threads

[Threads](/concepts/threads) supply the relevance query this design otherwise lacks.

"Related open commitments" scoped by project is noisy. Scoped by thread — *commitments
confirmed in the threads this session's memories belong to* — it is precise, because a
thread is by construction a continuous theme that cuts across scopes. The planned `thread`
filter on `search` and `thread` selector on `briefing` are exactly the primitives a
cross-session, cross-harness briefing wants.

The two designs are independent and compose: provenance answers *which episode produced
this memory*, threads answer *which theme it belongs to*. Sessions are episodes and should
not be modelled as threads.

## Explicitly not proposed

| Rejected | Why |
|---|---|
| Test/exit-code evidence capture | The one documented green-that-wasn't is the case it certifies wrongly. Belongs in the sub-agent prompt as a clean-checkout verification step |
| Reviving mechanical event capture | Settled 2026-06-11; the corpus damage is measured above |
| Sharing raw transcripts between harnesses | Codex states it outright: *"the transcript format isn't a stable interface for hooks and may change over time."* Replaying a full session also carries dead ends and stale assumptions at high token cost |
| New MCP tools for work state | `briefing`, `search`, `remember`, `resolve` and `handoff` already cover the jobs; the slot is spoken for |
| A SQLite/JSONL side store | A second system of record with a migration nobody needs |

## Plan

Sequenced so each step is independently useful and under the PR size guidance.

| # | Step | Validates |
|---|---|---|
| 0 | ~~Verify Codex exposes a blocking `Stop`~~ | **Done — it does.** Both harnesses support the design |
| 1 | Settle the typed provenance read (what a caller may project from `payload`) | Unblocks step 2; a policy call, not plumbing |
| 2 | Provenance on create/revise/resolve + the typed read | Attribution queryable; no migration |
| 3 | `Stop` triage behind the gate, one project, one harness | Recall against the 26% / 0% baseline |
| 4 | `SessionEnd` seal + delta cursor on `briefing` | Second session receives a delta, not a re-briefing |

**Validation bar.** Step 3 has a real baseline: 26% overall recall and 0% for commitments,
measured over 10 sessions. A re-run of that audit method is the pass/fail test.

**Do not ship step 3 ungated on Codex.** Codex's turn loop has no continuation cap, so the
gate is the only thing standing between this feature and an infinite loop.

## Open questions

- **The typed provenance read.** `rest.ts:311-322` forbids returning raw payload values.
  A projection limited to `session_id`/`agent`/`project` is the proposed resolution, but
  whether that is an exception to the rule or a narrowing of it needs deciding.
- **Gate tuning.** "Memories created > 0" may fire on sessions with nothing worth
  reconciling. Turn count or elapsed time may need to join the predicate.
- **Cost.** Every trigger is extra model turns plus tool calls on a session the user
  believed was finished. Worth measuring before it defaults to on.
- **Harnesses beyond Claude and Codex.** Unresearched. Cursor, Gemini CLI, Copilot, Amp,
  opencode and the VS Code agents were not surveyed, so it is unknown how many expose a
  blocking turn-completion hook at all. If most do not, MCP plus `SessionStart` injection
  is the fallback and the triage stays a two-harness feature.
- **Evidence provenance.** The corpus-damage measurements above come from the engram-era
  Python implementation, migrated into this corpus. The mechanism is gone from this
  codebase; the numbers describe the corpus it left behind.
