## Job and surface

An agent asked "why did you suggest that?" already holds the ids it used from `search`, `briefing` or `handoff`. It can request `get_memories` with `include: ["provenance"]` to trace where those memories came from. Each found item gains `provenance`; unknown and foreign ids both land in `notFound`.

REST `GET /api/v1/memories/{id}/history` returns the same object as `provenance`. Both surfaces call one core read. History retains its existing fields and graceful degradation: a failed provenance read yields `provenance: null` and `sections.provenance: unavailable`, without discarding readable history. Older servers may omit the additive fields.

The server returns recorded data. It never writes an explanation or summary of the chain. Synthesis stays with the client. Provenance contains no memory content, tags, embeddings, raw event payload or proposal rationale. Identity fields include topic, scope and project and are private to the caller; handlers never log the chain.

## Five sections

| Section | Contents |
|---|---|
| `origin` | The earliest own native `create` or importer `import` event: actor and time, plus the caller-owned `sessionRunId` and `run` (`agent`, `openedAt`) when present. Null when neither event exists. |
| `supersession` | Revision relationships as `predecessors` and `successors`: identity and validity, depth, edge id/endpoints/type/actor, recorded `sourceProposal`, and the related version's own creating session. |
| `events` | Newest audit events: id, kind, actor, time, caller-owned session and recorded `sourceProposal` (`proposalKind`, `proposalId`) or null. |
| `proposals` | Applied proposals naming the memory: id, kind, edge type/action, other memory id, creation/decision times, and `produced` edge/fact/event ids carrying that proposal's recorded reference. |
| `facts` | Fact id, validity and recorded `sourceProposalId`, without subject, predicate or value. |

`run.agent` is **reported by the session opener, not verified attribution**. An imported memory has `actorKind: importer`, no native run and no native proposal attribution. A malformed, deleted or foreign session reference returns null in this trace, even when an older history field preserves its recorded text. Nothing is inherited from a predecessor or a neighbouring event.

The cycle-safe revision walk covers the connected graph, including branches. Each selected edge appears once, oriented away from the inspected root. A step to the edge's `toId` is a predecessor relationship; a step to its `fromId` is a successor relationship. The related identity is the farther endpoint, and explicit `fromId`, `toId` and `edgeId` preserve orientation on equal-depth branches. Each version carries only its own creating run.

The read retains one parent edge per selected node before filling the edge budget with cross-links, so truncation cannot disconnect selected nodes from the root. Returned relationships are ordered by depth, then memory creation time, id and edge id. Events, proposals and facts use creation time descending and id descending. Product ids use creation time and id ascending. These tie-breakers keep capped subsets deterministic.

## Producer links

Acceptance records a producer only on rows it creates:

- `facts.source_fact_proposal_id` names the accepted fact proposal.
- `memory_edges.source_consolidation_proposal_id` or `source_retention_proposal_id` names the accepted edge producer; a CHECK allows at most one.
- Resolution accepts and retention archives record `proposalKind` and `proposalId` on their audit event. An edge acceptance that resolves a predecessor's commitment records the pair on that resolve event too.

Column references are nullable composite `(user_id, id)` foreign keys. Event references are an allowlisted pair, resolved against the caller's proposal table. A partial producer index supports event lookup by tenant, kind and id. This lookup follows the recorded link wherever an event landed: a commitment can move to a successor while a resolution acceptance is in flight.

Matching an edge or fact to a proposal by equal values or nearby times would fabricate attribution. Accepting an already-present edge produces no new edge; a crash between a resolution claim and transition can leave an applied proposal without an event. These proposals have empty `produced` arrays. Existing rows are not backfilled. Account exports preserve producer links; imports reject native attribution keys, and historical importer events never count as native producers.

Fact proposal staging has no production caller today; its table, review and accept path exist. Resolution and retention proposal producers remain default-off workers (`SESSION_CLOSER_ENABLED`, `FORGETTING_PASS_ENABLED`). The trace does not change those policies.

## Bounds and isolation

With provenance included, a call accepts at most **5 ids**; ordinary `get_memories` still accepts 20. The existing content budget also applies.

| Section | Bound per memory |
|---|---|
| Events | 50 |
| Proposals | 25 |
| Facts | 25 |
| Revision graph | 25 nodes including the root, 50 edges across both arrays |
| Products of each proposal | 50 ids per product kind |

Every bounded section reports `truncated`; products have `produced.truncated` too. Origin is a singleton. There is no cursor. Related memories receive identity fields only; trace their ids separately for their own events, facts and proposals. The worst-case response test fills every collection and text budget with JSON-escaping adversarial values and pins the complete MCP result, including its text mirror, below `MAX_GET_PROVENANCE_RESPONSE_BYTES` (8 MiB).

The complete read runs in one repeatable-read `withTenant(userId)` transaction, so concurrent acceptance cannot put different sections on different snapshots. Three batched provenance statements serve all roots. Every statement and recursive hop binds the caller's `user_id`, with RLS as a second layer. Session and event-proposal lookups also bind `(user_id, id)`; an unowned root cannot probe whether another account has that id. UUID payload references are safely decoded before indexed UUID comparison.

The existing `get_memories` tool owns this job; no new tool or gated tool-selection scenario was added. Its generated reference, transport snapshot and description embeddings cover the changed surface. The five `get_memories#provenance` capability scenarios are report-only, alongside `revise#disposition`.

## Synthetic evaluation design

[#432](https://github.com/B3dmar/3ngram/issues/432) adds a scripted two-tenant fixture at `eval/fixtures/provenance-synthetic.json`. Both tenants use matching topics and shapes. Product writes cover attributed remember, more than 25 revision versions, move/archive/reaffirm, and each accepted proposal kind.

The blocking integration test maps fixture labels to created ids and scores `provenance_chain_recall` and `provenance_chain_precision` at 1.0, with `provenance_foreign_ids` at 0. The long chain must report truncation. Mutation checks must catch a removed caller predicate and a dropped producer link. This is a database-backed integration slice, not part of the network-free, database-free `eval-gate`.
